# 踩坑与失败方案（PITFALLS.md）

本文档记录本汉化项目中失败的做法、误导性假设、脆弱流程与兼容陷阱。目的是保存**负面知识**。

条目按模板记录；失败方案不因最终采用别的方法而删除。

## 1. 字符表 index ≥ 1280 出现"粉色 @"（扩格未改 exe）

**状态：** 已验证
**影响范围：** 字体 / 资源格式
**症状：** 把字符表 index 1280–1407 的空位改成简体字后，原本显示 `?` 的字变成**粉色 `@`**，无一个字变汉字。
**初始假设：** 只要图集有空位、字符表有空槽即可扩格。
**实际原因：** exe 建表循环 `cmp edi,0x13FC` 硬跑 **1280 次**，二分查找上限常量 `0x4FF(=1279)`；
坐标表只有 1280 项。index ≥ 1280 能被字符表命中，但坐标表未初始化 -> 垃圾坐标 -> 粉 `@`。
**失败做法：** v2.6 只改图集与字符表、不改 exe。
**正确解法：** 必须改 exe（见 v2.8 起）。
**如何检测：** 装机后看是否有粉 `@`；`ascii_reserved()`/坐标表项数核对。
**回归测试：** 覆盖率统计 + 进游戏抽检。
**相关文件：** `build_cn.py`（`UNLOCK_1280` 注释块）、`历史报告（未入库）：汉化补丁v2.6-扩字格实验说明.md`。

## 2. 扩容到 4096 后"启动即闪退"（循环上限差 1）

**状态：** 已验证
**影响范围：** 可执行补丁 / 字体
**症状：** v2.11（2048×2048 图集）、v2.12（1024×1024 图集）改装后**游戏启动即闪退**。
**初始假设：** 图集尺寸超限（引擎单边上限 1024~2047）导致闪退。
**实际原因：** 建表循环上限写成了 `N*4`。该循环为 `cmp edi,L; jl`（`edi=4i-4`），
迭代次数 = `L/4 + 1`，**正确值必须是 `4N-4`**（原版 1280 用的正是 `0x13FC=4*1280-4`）。
写 `N*4` 会多跑一轮 `i=N`，把排序表指针写到 `.atbl` 节末尾之外 -> 越界写 -> 访问违例 -> 闪退。
**失败做法：** v2.11/v2.12 反复改图集尺寸，均未命中真因。
**正确解法：** v2.13 把循环上限改为 `4N-4`；并用逐位证明确认 4096 索引与图集格双射不重叠。
**如何检测：** 启动即崩；反汇编循环边界。
**回归测试：** 启动 -> 进菜单 -> 进关卡；`design`/verify 脚本核对索引唯一性。
**相关文件：** `build_cn.py: patch_exe_unlock()`、`历史报告（未入库）：汉化补丁v2.11/2.12/2.13*.md`。

## 3. 跨图集搬迁导致省略号"蓝绿描边"

**状态：** 已验证
**影响范围：** 字体
**症状：** 扩格后省略号 `…` 等符号出现蓝绿色描边。
**实际原因：** v2.13 的取格公式把 index 1024–1279 从图集 A 换到了图集 B，
而两页调色板不同（A 的 idx19/20 = 灰，B 的同名 idx = 青绿）-> 串色。
**正确解法：** v2.14 换一套取格公式（`shr ecx,11` / `V&63` / 页号 `62+bit10`），
让**原版字形一格不跨图集**，跨图集搬迁数 = 0。
**如何检测：** 观感比对；调色板索引核对。
**相关文件：** `build_cn.py`（`game_cell()`/`old_cell()`/`LAYER`）、`历史报告（未入库）：汉化补丁v2.14*.md`。

## 4. 定长槽"多写几字节"清零相邻 int 字段 -> 选关/选章闪退

**状态：** 已验证
**影响范围：** 资源格式 / 补丁
**症状：** 选章节/选关进入时闪退。
**实际原因：** 两次同型事故——
- v2.59：章节名槽写 68 字节，真实容量 64，多写的 0 清掉 `pos68` 的**世界/章节组编号**（73/85 条非零）；
- v2.61：村落表地名槽固定写 40 字节，真实容量 32（184 条），多写的 0 清掉 `off136` 的**关卡/幕编号**（64 条）与 `off140`（49 条）。

游戏按这些编号索引资源，得 0 -> 越界 -> 闪退。
**正确解法：** 容量取**保守最小值**（章节 64 / 地名 32）；写入只覆盖到字段边界，
并加"写后越界守卫"（把紧随其后的 4 字节按原样回填）；体检新增 `cscv[28] off136/off140` 检查。
**如何检测：** 写后 diff 审计（差异须全落在登记槽内）+ 体检。
**回归测试：** 选章/进入关卡不闪退。
**相关文件：** `build_cn.py: CSCV_CHAP_JOBS / apply_cscv_place() / CSCV_PLACE_LEN`、
`历史报告（未入库）：闪退修复报告-v2.61-20260917.md`。

## 5. cscv "内容匹配同步"误伤脚本层键名 -> 机制断链

**状态：** 已验证
**影响范围：** 资源格式 / 补丁
**症状：** 同伴不能攻击/用技能（v2.28）；选关"勇者城"消失（v2.64）。
**实际原因：** `cscv.s2a` 中有一批与 `LANG_JA` **逐字节相同**的 blob；它们其实是**脚本/数据层**，
游戏按 CP932 原码做按名比对。构建的"内容匹配同步"把 LANG 侧译文（载体码）写进了这些孪生 blob，
字符串彻底改变 -> 按名比对失败 -> 机制断链。
**失败做法：** v2.28 把 cscv 与 LANG 一起改。
**正确解法：** 同步时**跳过键名类槽位**（`cscv_skip_keys`，判据 = 原文 ∈ collide）；
对内容匹配配不上的孪生表**显式按 cscv 索引写入**（`CSCV_CHAP_JOBS`），并只写显示字段。
**如何检测：** cscv md5 写前写后断言；cscv 孪生名字键字段断言为日文原版。
**相关文件：** `build_cn.py`（v2.64 `cscv_skip_keys`、`CSCV_CHAP_JOBS`）、`tools/fix_954.py`。

## 25. 名字中文化实验的失败与陷阱（2026-10-19）

**状态：** 已验证
**影响范围：** 翻译 / 构建 / 逆向
**背景：** 为让技能/装备/称号名上屏中文，做了 Z1–Z9 一系列对照包。以下每条都是
**实机或字节级验证**过的，避免后人重踩。

### 25.1 按名查找不是字符串比较，而是哈希比较

- 引擎用 **名称 → CRC-32** 再比 32 位值（exe `0x46C070` / `0x46C0C0`），且大量调用点是**内联**的。
- 因此：**钩 strcmp/strncmp/CompareStringW 抓不到它**（实测整场游戏零调用）；
  只能从数据一致性（两边同名）来判断是否断链。

### 25.2 译名重名 = 静默串味（已修）

- 两个不同英文名译成同一中文名后，哈希查表会落到错误条目。
- 实测症状：序章主角**莫名获得「英雄斩」**（`Brave Blade` 被译成与 `Hero Sword` 同名的
  「勇者之剑」）、伙伴贴图/特效异常。
- **修法：** 译名必须全局唯一（同一原文可重复，不同原文不可同译）。
  2026-10-19 已修 `text_v2.csv` 133 行（含 `Wood Stick`→木杖、`Warrior`→勇士、
  `Lancer`→长枪兵、`Marksman`→神射手、`Brave Blade　`→勇者战刃 等）。
- **注意：** `locales/zh-CN/replace_map.py` 的子串替换会二次制造重名
  （例 `木棍`→`木棒` 会撞 `Club`），改译名后必须按**最终写入字节**复查。

### 25.3 副本必须全部同步，只翻一半必坏

- 武器表 `+168/+204/+236` 是技能名副本；章节脚本里还有 `head=/body=/handR=/handL=/foot=` 的装备名。
- 只翻技能表而不翻武器表副本 → 技能"只有名字、无动画无效果"（官方 EN/JA 都是全同步的）。
- 只翻装备表而不翻脚本 loadout（或反之）→ 序章**初始装备丢失**、伙伴不显示。

### 25.4 `b666 +288` 不是长度字段！

- 它是**语言无关的数字 ID**（EN/JA 87/87 相同，如 `Drain Axe`=15）。
- 曾误当"字符串长度"改写，并把记录尾部（`FF×8` + 3 个 u32 元数据）清零 —— **87/87 条全毁**，
  实机表现为"习得技能全部丢失、武器技能连名字都没有"。
- **教训：** 改任何定长记录前，先用 EN/JA 对照判断字段是否语言相关；不要凭"看起来像长度"下手。

### 25.5 `+292` 键名不能中文化（本作）

- 官方 JA 把 `+292` 也写成日文，但这依赖其"参照侧"（`cscv`/脚本层）**同时**本地化。
- 我们只在 `LANG_EN` 上做中文、`cscv` 保持原版 ⇒ 键名改中文后：
  **技能能被查到（名字在），但效果/动画解析失败**（实机）。
- ⇒ 正确做法：**`+292` 保持原版**（现行 Z4 配方）。

### 25.6 大范围"整槽替换"会打断脚本

- 以"文本完全相等"为判据的全文件替换（Z1）会把脚本里的同名令牌一起换掉，
  导致序章事件开始即**空指针崩溃**（`0x4714CA`，`0x471440` 查 `FlagOffDraw` 等节点返回空）。
- ⇒ 替换必须有**列级/表级白名单**，不要跨脚本 blob 盲目替换。

### 25.7 跨包不能按字节比较差异

- 中文载体码按**字频**分配；`text_v2.csv` 一变，全文件字符码整体平移。
- ⇒ 比较两个构建产物必须按**槽位语义**（解码后文本）比较，不能直接 diff 字节。

### 25.8 换语言路径不能规避演出瑕疵（2026-10-19）

### 25.10 名字哈希操作数重算的坑（2026-10-21，已验证·离机）

Z10 实验配方（`apply_names_cn_keycol_hash` = Z9 + `recompute_name_operands()`）落地时踩到：

1. **不能用原文/UTF-8 译表算哈希** → 必须用**最终写入的 CP932 载体码字节**。
   引擎 CRC-32（exe `0x46C070`）对高字节做**符号扩展**：纯 ASCII 与 `zlib.crc32` 相同，
   CP932 汉字字节不同（`爆散` 实测 `CE79A017` vs zlib `5DE38477`）。
2. **未排除语言无关内部键** → 初版把 `b83` 等 11 个 JA==EN 的操作数当成名字去解析，
   产生 31 个"源串未解析"误报。判据：母本 `LANG_JA` 同位置取值相同 ⇒ 跳过（Z10 跳过 49 个）。
3. **副本同步集合漏表** → `Hero Twin Buster` 等 3 个名字在 `b391`（网络技能名表）仍是英文，
   其余副本已中文，重算直接中止。`sync_name_replicas` 的 `single_slot_blob_allow`
   必须含 `391`；判据是"该名字出现的**全部**槽"，不是"装备/技能表"。
4. **CSV 假文本槽覆盖操作数** → `text_v2.csv` 有 2 行把 EN 操作数字节 `4E 75 65 15`
   当成文本槽读出 `Nue`，并写入 `夜`：
   - `blob 417`，`offset 25364`（= `16 + 88*288 + 4` 操作数起点）
   - `blob 654`，`offset 16724`（= `16 + 58*288 + 4`）
   `do_apply` 会把 2 字节中文 + NUL 写进这 4 字节，直接改坏哈希。
   Z10 的"名字未翻译 ⇒ 恢复原值"回填修复了这 2 处。**这 2 行已于 2026-10-21 从 CSV 删除**，
   并重建 Z10 与默认包：重建后回填数为 0，默认包的这两个操作数已恢复原值
   （`b417 rec88`/`b654 rec58`：JA `1A5CF8B4`、EN `1565754E`）。
   **教训：** 定长记录里的 u32 操作数必须从文本槽枚举中剔除，CSV 只登记真实文本槽。
5. **`b954` 是键表，不要当"副本漏同步"** → 伙伴表 `b954`（CSCV、stride 236、44 条）
   含 `+4` 名字 / `+136` `X Resident` / `+168` `X Skill`，**不在 `text_v2.csv` 中**。
   Z10 后 LANG 里 `Knight` 的 236 个副本 = 235 个显示位（中文）+ 1 个 `b954` 键表位（英文原样），
   这是**设计状态**。
6. **`b756` 的 4 个操作数无解**（rec0/3/91/94） → EN 全资源中找不到对应串（JA 侧可解析为 `爆散`），
   判为二进制载荷巧合，保留原值；不要为此放宽严格断言。

**离机结果：** 重算 168（`b83`=84 / `b394`=84）、回填 0、名字未变 92、内部键 49、
未解析 4、副本不一致 0；逐点复算 260 点全对。**实机结论仍待验证。**

**相关文件：** `tools/build_cn.py`（`recompute_name_operands()` / `apply_names_cn_keycol_hash`）、
`build/_scratch/verify_z10.py`、`TECHNICAL.md` §10.3.7、`locales/zh-CN/text_v2.csv`（2 行假槽）。

### 25.11 Z10 实机后：旧“机制名”结论被混淆变量污染（2026-10-21）

**Z10b 实机结果（2026-10-21，已通过）：** 只放行技能/装备名 + 操作数重算、伙伴名与其余

⇒ **“装备名或技能名一翻就坏”的旧结论是被伙伴名等变量污染的相关性，不是已证因果。**

**未登记名字副本仍未处理：** `b892`（stride 288、223 条）`+28` 装备视觉部件名在 Z10 后

### 25.13 Z11 伙伴名实验的实现陷阱（2026-10-21）

### 25.14 `mirror=True` 连带关闭称号/Q16 守卫 → 称号无法获得（2026-10-21）

**症状：** Z10b/Z11/Z12 实机中称号列表变成中文，且新称号无法获得
（`b931 pos0` 实测 191/252 条被改写）。
**根因：** `rewrite_text()` 的章节/称号守卫条件写成了 `if (not mirror) and ...`。
`mirror=True` 原本只是为“照抄官方 EN 的 `b666` 键名列”而设，却**同时关闭了
`chap_title_guard`（称号/Q16）**。Z10/Z10b/Z11/Z12 全部使用 `mirror=True`，
因此从 Z10b 起称号就被翻译；用户直到 Z12 才检查。
**修复：**
1. `rewrite_text` / `do_apply` 增加 `title_guard=True` 参数，条件改为
   `if (title_guard or not mirror) and ...`；仅 E2 镜像实验显式传 `title_guard=False`。
2. `fill_name_copies()`（按内容补齐副本）也必须跳过称号/Q16/技能键列，
   否则即使 `do_apply` 保住了 `b931`，补齐阶段仍会把同名标题写中文。
3. 修复后重建 Z10b/Z11/Z12：`b931 pos0/pos36` 改动均为 **0**。
**教训：** 一个“放行开关”不要顺带关闭安全守卫；任何按内容写名的收尾步骤
都必须复用同一套守卫（collide/称号/Q16/键列）。

### 25.15 副本补齐必须跳过 `skip_blobs`（职业/阵型/连携技键表，2026-10-21）

**症状：** Z12 实机中职业 `Hero` 显示为「勇者」、其它职业仍英文；阵型 `Speed Eater`
显示为「速度吞噬者」、其它阵型仍英文。
**根因：** `fill_name_copies()` 为“按内容补齐全库同名副本”而扫描全部 blob，
未跳过 `skip_blobs=(128,136,317)`。`Hero` / `Speed Eater` 恰好在批次 A 的显示列里
（`_z12_names_en` 收录），于是被补进职业/阵型**键表**；Z11 的伙伴名补齐也把

## 27. 载体码重排会让存档里的自定义名字变字（2026-10-22）

**状态：** 已验证（机制与症状一致）
**影响范围：** 字体 / 存档兼容
**症状：** 玩家把主角改名为「尤莎」，安装新打包的补丁后，名字偶尔变成「允莎」等
相邻字；重新改名后又可能在下一次补丁变化。
**实际原因：**
- `build_plan()` 按**字频** `cnt.most_common()` 给汉字分配载体码（`cmap[ch]=pool[k]`）。
  译表、额外行、歌词/DLC 用字任何变化都会改变排序，导致大量字的 CP932 载体码平移。
- 游戏内文本每次构建都会按新 `cmap` **重新编码**，所以显示正常；
  但玩家自定义名字保存在**存档里的是 CP932 字节**，补丁不会重写存档。
  新补丁的 `cmap` 把这些旧字节解释成别的字 → 名字变字。
- 实测 Z13→Z14：2,818 个装库汉字中 **2,526 个载体码发生变化**。
  例：Z13 的「尤」= `95 58`，在 Z14 中 `95 58` 解码为「渡」；
  Z14 的「允」= `95 59`，所以旧存档里的「尤」字节很容易变成「允」。
  ASCII 名字（`Yushia`/`Yuja`）不受影响，因为 ASCII 不参与载体码重排。
**为什么“偶尔”：** 只有字频排序发生变化的字才换码；相邻字的码可能恰好不变，
所以不是每个名字、每次补丁都肉眼可见。
**正确解法（尚未实施）：** 固化 `cmap`（append-only）：
- 把某一版的 `字 → 载体码` 映射持久化（如 `locales/zh-CN/cmap.json`）；
- 构建时优先使用固化码；新字只从**未使用**的码/格追加，绝不重排已有字；
- 容量不足时只能用同义词替换/拒绝新字，不能挤掉旧码（当前余量约 51 格）。
- 在固化前，玩家改名只能临时规避，下一次补丁仍可能漂移。
**如何检测：** 连续两次构建后比较 `cmap` 中同一汉字的码；或读存档名字字节，
用新旧 `cmap` 反查是否同字。
**相关文件：** `tools/build_cn.py`（`char_freq()` / `build_plan()` 的 `most_common` /
`PITFALLS.md` §10）、`docs/KNOWN_ISSUES.md` §13。

### 25.26 视频硬字幕：yuv444p 被游戏静默跳过；VFR/结尾长帧导致音画不同步

**已验证（2026-10-24）：**
- 游戏电影播放器只接受 **Theora yuv420p**。ffmpeg 默认 overlay + libtheora 会输出
  **yuv444p**，游戏不报错，直接跳过整段视频。必须加 `-pix_fmt yuv420p`。
- 原视频是 **VFR**：开头有 0.4s 长帧，结尾最后一张静帧可长达约 5s；容器/音频
  时长（如 91.70s）比最后一张非重复视频帧（86.6s）长。直接用 `-shortest` 会把视频
  截到 86.6s 甚至更短，导致 BGM 截断、剧情相对音频提前。
- **不要用 fps=30 / 二次编码 / `-t`**：会重写 VFR 时间轴，造成中段跳帧、杂音、
  对话早于音频。当前做法是 **单遍** `ass`（+ RAGNAROK 静态 drawbox）→ libtheora，
  保留原帧时间轴；末尾只加 `tpad=0.7` 克隆最后一帧，保证 BGM 不在视频 EOS 处被截断。
- 硬字幕不可能做到“绝对零时长偏移”：重编码仍会丢失约 0.3–0.4s 的末尾长静帧，
  所以用 tpad 补到略晚于音频。若要求完全不动视频/音频，只能用运行时字幕叠加。
- 开场剧情采用 **不改原文** 的方式：只在左上角加整段中文，原英文滚动/淡入淡出全部保留；
  中文放左下会被滚动的原文压住，放顶部中间会在后段被压住，左上角窄栏是最稳的。
- ASS 的 `\move(x1,y1,x2,y2,t1,t2)` 时间是 **相对事件开始**，不是绝对时间。
- 本 ffmpeg 构建的 `drawbox` **y 表达式不按帧求值**；不要用它做移动遮罩。
- **已知残留（Open，暂不解决）：** 单遍方案下 RAGNAROK 对话仍略早于音频，
  见 `docs/KNOWN_ISSUES.md` §20；中段卡顿/杂音已消除。
- 片头 26s 的 5 句不要加黑底；只叠带描边的中文，避免遮住画面。
- **开场中文字体（2026-10-24）：** 用系统字体 `C:\Windows\Fonts\屏显臻宋.ttf`（族名
  `Clear Han Serif`），字号 34。Pillow 对这套字体 `getname()` 返回 `'????'`，所以
  `_font_family()` 直接解析 sfnt `name` 表的 nameID 1（优先 platform 3 / lang 0x409）。
  ASS 的 `Fontname` 必须写 `Clear Han Serif`，字体文件复制进 `fontsdir` 即可被 libass 命中。
- **开场行序必须跟原片一致（2026-10-24）：** `pro_scroll2` 原片顺序是
  `The world was at peace.` → `However,` → `time marches on...` → `Goddess Era 600`；
  中文也必须按这 4 行顺序写，否则玩家对照原文字幕时会觉得“错行”。
- 工具：`tools/build_video.py`；隔离测试包：`tools/package_video_test.py`。
